# StreamRD v0.23.0 — An Update button

**Admin → System → Updates** now has an **Update** button that does the whole update for you, instead of a command to copy and run.

- **One click.** Press **Update to vX**. StreamRD takes a verified backup, downloads the new version, restarts into it and checks that it starts. The page reloads by itself when it is done, in a minute or two.
- **A safety net.** The old container is kept until the new one is healthy. If the new version does not start, the old one is put back automatically and the page tells you; nothing is lost either way (settings in `config` and downloads in `data` are never touched, and the database is backed up first).
- **How it works.** The small helper that starts Plex and Jellyfin (the media manager) now also replaces the StreamRD container, because only it holds Docker access. It can replace only the one container named `streamrd`, only with a newer image of the exact reference that container already runs, and keeps the same ports, folders, settings and network. The caller chooses nothing.
- **Who has it.** New installs include the helper, so the button is there from the start. On an existing install run `bash install.sh --media-manager` once (the Updates box says so). Until then the box shows the command to copy, as before. An operator's own `UPDATE_WEBHOOK_URL` still wins.

## Nothing is lost or rewritten
No migration. The helper itself is refreshed the next time you run `install.sh` or `docker compose up -d`; an older helper cannot update StreamRD, so run `install.sh --media-manager` once after upgrading to v0.23.0 if you added it earlier.

## Upgrading
`docker compose pull && docker compose up -d` (the last time you need to do it by hand), then `bash install.sh --media-manager` to refresh the helper.

## Verification
New tests: against a fake Docker engine that keeps state, the helper replaces the container with the new image and keeps its ports, folders, settings, labels and networks (leaving what the old image supplied to the new one), removes the old container only after the new one is healthy, does nothing when the image is already the newest, restores the previous container when the new one does not start or cannot be created, answers only with its secret, runs one update at a time, and refuses other methods; the server uses the helper as the updater when no hook is set, backs up first and never returns the helper's token, and an operator's hook still wins. Not verified: a real Docker host and a real image pull, which no CI here can do; the first real press of the button on your machine is the true test, and the old container is only deleted after the new one is healthy.
