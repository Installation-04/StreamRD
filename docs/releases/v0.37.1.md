# StreamRD v0.37.1 — converted videos no longer stop after about a minute in Firefox

## What was wrong
A video that the server converts while you watch (the DTS and MKV files) played for about 45 to 55 seconds in Firefox and then stopped with "This browser could not play this file", although the server and the stream were fine. Your diagnostics showed it every time, always about a minute after the video started.

The cause was in the container's front door, the small program that passes requests to the web app and the API. It gave up on the connection to the API after 30 seconds without any traffic. A converted video is one long answer, and Firefox stops reading it for as long as it has enough picture buffered ahead; after 30 quiet seconds the front door cut the connection and the player saw a network error.

## What changes
- The front door only waits for the **first bytes** of an answer (30 seconds, and 2 minutes for a converted video, whose first bytes can be slow when the provider is slow). Once the answer has begun it is never cut for being quiet.
- Chrome and other browsers were reading steadily and rarely hit it; they benefit too when they pause (a paused video, a background tab).

## Not done yet
Firefox still has to fall back to a plain video tag for converted videos on some machines ("The video's header names no codecs this player knows" in the log, a few seconds after the start); the video plays, only without the finer seek bar of the streaming player. If you run StreamRD behind your own proxy (Caddy, nginx, Traefik), check that its read and idle timeouts are not shorter than a few minutes for `/api/stream/`.

## Nothing is lost or rewritten
No migration and no setting. A new small file (`gateway.cjs`) in the image; the front door's behaviour is otherwise unchanged.

## Upgrading
`docker compose pull && docker compose up -d`, or the **Update** button. The Update button restarts the container.

## Verification
- A server test starts the front door in front of a stand-in program that answers, goes quiet for longer than the wait, then answers again: the whole answer arrives. With the fix removed the same test fails (the answer is cut after its first part). Further tests: a program that never answers gets a plain 503; a converted video's first bytes get the longer wait; `/healthz` and routing to the web app are unchanged.
- The container start-up tests still pass.

**Not verified:** playing a long converted video in Firefox after the update (no Firefox in the build environment): please check that one video plays past the one-minute mark.
