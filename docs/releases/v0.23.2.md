# StreamRD v0.23.2 — Converted videos that stopped when resumed or sought now play

A video the server converts could play from the beginning and still fail the moment you resumed it or moved the seek bar, with "This browser could not play this file" and nothing from the server. The cause is found and fixed.

- **The cause.** When only the audio needs converting (an MKV with H.264 and DTS, for example) the picture is copied untouched, and a stream that starts part-way in begins at the nearest earlier keyframe. In many H.264 files, Blu-ray style encodes above all, those keyframes are not clean starting points: the frames after one still refer to pictures before it. Desktop players hide that. A browser stops with a decode error. The server saw nothing wrong, which is why v0.23.1's message had nothing to say.
- **The fix.** When the browser reports a decode error on a copied picture, the player asks the server once to convert the picture as well from that moment, and carries on. It keeps doing so for the rest of that video, so later seeks do not fail first. The title bar then reads *Converted for your browser*, and **Admin → Logs** (type *playback*) records that it happened.
- **A refused stream now shows its reason.** When the server refused a converted stream (expired, busy, or a conversion that failed at once), the player showed a black page and no message, because browsers report that on a different element from the one the player listened to. It now shows the help box with what the server said.
- **If picture conversion is turned off** (`TRANSCODE_VIDEO=false`), the player says that this video needs it instead of failing without a reason.

Playing a converted video from the very start is unchanged, and so are files that play directly.

## What it costs
Converting the picture uses much more processor than copying it and is capped at 1080p. It only happens for files that need it, and only after you resume or seek in them.

## Nothing is lost or rewritten
No migration. No setting changes.

## Upgrading
`docker compose pull && docker compose up -d`, or the **Update** button if you added the helper.

## Verification
- Reproduced in Google Chrome 153 on Linux with software decoding: an open-GOP H.264 + DTS MKV plays from the start, fails with `PIPELINE_ERROR_DECODE` when started part-way in, and plays from the same moment once the picture is converted. The same file encoded with closed GOPs plays part-way in without help, which isolates the cause. See [the investigation](../playback-investigation.md).
- New server tests (real ffmpeg, with a decoder as strict as a browser's): the copied stream is clean from the start and not from the middle, the converted one is clean from the middle, the log line carries no link, and the request is refused with a reason when picture conversion is off.
- A new browser check, `qa/converted-playback.cjs`, runs those four cases against the server's real stream route in Google Chrome and now runs in CI. The conversion tests also run in CI for the first time: they used to skip themselves there because ffmpeg was not installed.

Not verified:
- **The owner's own failing file.** This is a confirmed cause that matches the report (H.264 with DTS, converted on the server, refused by the browser, no server error). Whether it is the cause for that file is confirmed only by playing it on this version. If it still fails, the help box and the log now show what the browser or the server said.
- **The player page itself in a browser.** The change to the player is type-checked and built; the browser check drives a small page that follows the same steps, not the React component.
- **Hardware decoding, and other browsers.** Chrome with GPU decoding, Firefox, Safari and Edge were not run. They may accept some streams that software decoding refuses; the fallback only acts when a browser reports a decode error.
- A converted stream held paused for 40 seconds through the gateway kept playing; longer pauses were not tried.
