# StreamRD and Phosphor v0.24.0 — The server is run from its web page, in one container

After the one-time install, changing how the server behaves should not need a command or a file on the machine. This release moves the first set of those things to the pages, and puts the helper that does the work inside the StreamRD container: **one container, no extra script to start any component.**

## One container: Docker control is built in
Until now, starting Plex or Jellyfin from the page, the **Update** button and the new **Restart** button depended on a second container (`streamrd-media-manager`) that the installer added next to StreamRD. That helper is now part of the StreamRD image and runs inside its container.

- **How.** The container is given Docker's socket and starts as root. Its first program starts the helper as root and runs StreamRD, Phosphor and the download client as user 1000, as before. The helper alone opens the socket; it listens only on the container's loopback address, with a secret made anew at every start and handed only to the two API processes. It finds where StreamRD's folders are on the machine by asking Docker about its own container, so a volume or a path you chose is used as it is.
- **Updating.** The helper cannot replace the container it lives in, so it starts a short-lived updater from the image that is running: it gets Docker's socket and nothing else (no network, no folders, read-only, no capabilities). The updater stops, renames, creates and health-checks as before, rolls back if the new version does not become healthy, and is removed by the new container, which copies the account of the update into **Admin → Logs**. Because the helper is part of the image, **every update brings the new helper with it**, and `docker compose pull && docker compose up -d` does exactly what the button does.
- **On by default, and declinable.** A new install has it. `--no-media-manager` takes the socket and root away again; `DOCKER_CONTROL=false` switches the helper off without touching the socket.
- **Moving an install that had the second container.** Run the installer again. It removes the old overlay file, the secret and the folder setting from `.env`, says so, and `docker compose up -d --remove-orphans` (done for you, unless `--no-start`) removes the old container. Media servers already started are not touched. A setup that points `MEDIA_MANAGER_URL` at a helper elsewhere keeps working.
- **Rootless Docker**, Docker Desktop and Podman: the installer records where the socket is (`DOCKER_SOCKET_PATH`); `docker run` users add `--user 0:0` and the socket.
- **What it does not protect against.** Inside the container the boundary is between two users, not two containers: a flaw that gave someone root inside it would give them Docker, and Docker is the machine. [Docker control](../plex-jellyfin.md#docker-control) says what the helper can do, what is kept from it, and what to do before exposing a server to the internet. Where the socket on a machine is open to user 1000 (so the boundary does not hold), the page and the container's log say so.
- **Why Plex and Jellyfin stay separate containers.** They are large programs with their own releases (Plex is closed source); the pages start them next to StreamRD from a fixed specification.
- **What still needs the host, once.** The very first install, and giving an existing install without Docker access its socket: the app cannot give itself access to Docker. The page shows the one command; it is the installer, run again.

## Server settings, in Admin → Server
These used to exist only as environment variables. They are now choices on the page, in force the moment you change them, and kept across restarts and updates:

- **Convert files a browser cannot play**, and **also convert the picture when a file needs it** (StreamRD).
- **Videos converted at once**, from 1 to 8 (StreamRD).
- **Let the server read media links on its own network**, for a source at a local address (StreamRD).
- **Check in the background that links still work.**
- **Check for new versions.**

Each line says where its value comes from: chosen on the page, set in the server's environment, or the default. If your install sets one of the variables (`TRANSCODE`, `TRANSCODE_VIDEO`, `TRANSCODE_MAX`, `TRANSCODE_ALLOW_PRIVATE_HOSTS`, `LINK_HEALTH`, `UPDATE_CHECK`), it keeps working exactly as before until you choose something on the page; *Use the default* forgets a choice.

## Restart, in Admin → System
A **Restart the server** button, and *Restart now to apply* after staging a restore, work wherever Docker control is on. Until now they needed `ADMIN_RESTART=true`, which the standard install did not set, so a staged restore had to be applied by restarting the container by hand.

## Plex and Jellyfin
- **Start again with the machine, or not.** Each server has a switch, on by default: after a reboot or a restart of Docker the media server comes back by itself. Turn it off to keep it stopped until you launch it from the page. It can be changed for a server that is already running; nothing else about the server changes.
- **The launch is followed in a log box** under the buttons: the image download with its progress, the start, then the server's own output, with a *Copy log* button. This existed since v0.23.0; it is now exercised in a real browser on every pull request.

## Nothing is lost or rewritten
No migration. One stored value is new: the choices made in Admin → Server.

## Upgrading
- **No helper yet, or the helper in a second container (v0.21.0 to v0.23.2):** run the installer again (`curl -fsSL https://raw.githubusercontent.com/Installation-04/StreamRD/main/install.sh | bash`). It keeps your settings, ports and data, turns Docker control on (unless you declined it before) and moves the helper into the StreamRD container.
- **Already on v0.24.0 with Docker control:** `docker compose pull && docker compose up -d`, or the **Update** button. Nothing needs doing by hand; the helper is part of the image.
- **Until the installer is re-run**, an install with the second container keeps working as before, except that restart and the start-with-the-machine switch need the newer helper: the pages then say the helper did not accept the request.

## Verification
- **The owner's journey in Google Chrome, now 21 steps**, on every pull request. The two new steps run the real helper against a stand-in for Docker: Jellyfin is launched from the page, the log box shows the download, the start and the server's output, the start-with-the-machine switch is turned off; then a setting is changed and reset from Admin → Server, and the server is restarted from Admin → System, which reaches the helper.
- **Against a real Docker daemon, on every pull request** (`infra/smoke-docker-control.sh`): the container starts as root with the socket; only the helper is root and user 1000 cannot open the socket; Jellyfin is launched from the web API (real image, folders mounted from where the volumes really are, answering on its port, restarting with the machine unless told otherwise); the server is restarted from the web API and comes back with its data and Jellyfin untouched; an update to an image that never becomes healthy is rolled back with nothing lost; an update to a good image is applied by the updater, the new container keeps its user, restart policy and mounts, the updater is removed and the outcome is in the log.
- The container's first program is tested running for real when the tests run as root (they did on the development machine; GitHub's runners are not root, so there the real-Docker check above is what covers it), against a stand-in for Docker: the helper stays root with none of StreamRD's secrets, StreamRD runs as user 1000, cannot read the helper's memory or stop it, a stop reaches StreamRD, and the helper is started again if it dies. The helper's updater is tested by running its own program against a stand-in that keeps state.
- Server tests: StreamRD and Phosphor server suites, with new tests for the helper inside the container (finding its container, folders and network, the updater hand-over, rollback, a half-finished update), the container's first program, and the installer moving a two-container install into one. New ones cover each setting's source and effect without a restart, saved choices surviving a restart, unreadable stored values, the update check making no request when off, restart through the helper (accepted, busy, not answering) and through a declared supervisor, and the helper's restart and start-with-the-machine actions with a stand-in for Docker.
- `bash infra/test-install-script.sh` and the shared-file check pass.

Not verified:
- **A reboot of a real machine.** The pull-request check restarts the container and starts a real Jellyfin, but a media server coming back after the *machine* reboots rests on Docker's restart policy, which the check sets and reads back, not on a reboot.
- **Docker Desktop, rootless Docker and Podman**, and a socket whose group is 1000. The installer's choice of socket path is tested with a stand-in; nothing was run on them.
- **Plex.** Launching it uses the same code as Jellyfin with its own fixed specification and claim token; only Jellyfin is started for real by the check.
- **Phosphor's pages in a browser.** Its settings card is the same component; it was type-checked, not clicked.
- Other browsers than Chrome.
