# StreamRD v0.23.1 — Converted videos that failed now say why, and open requests no longer pile up

A video the server converts (MKV, DTS and so on) could still fail in the browser with no explanation. This release fixes what can cause that and makes the rest visible.

- **A browser's duplicate requests no longer use up the limit.** A browser often asks for one video several times (to look at it, then to play it). Each ask started its own conversion and counted against `TRANSCODE_MAX`, so the extra asks could be refused and the video failed. Now the newest request for a video replaces the older one.
- **Nothing is sent until ffmpeg has produced video.** A conversion that fails at once used to answer with an empty video, which a browser reports only as "could not play". Now the server answers with the reason.
- **The player tells you why.** When a converted video fails, the help box adds **What the server says** (ffmpeg's own message, with the link taken out). The same message is written to **Admin → Logs** (type *playback*) and to `docker logs`.
- **Fragment timestamps made safer for Chrome.** Converted streams now use negative composition offsets and a larger muxing queue, which avoids a timestamp error browsers can raise on H.264 with B-frames.

## Nothing is lost or rewritten
No migration. Nothing changes for files that play directly.

## Upgrading
`docker compose pull && docker compose up -d`, or the **Update** button if you added the helper.

## Verification
New tests: a conversion that fails at once answers 502 with ffmpeg's message and no link, and the status endpoint tells the player the same; the newest request for a stream replaces the older one while a different stream is still refused at the limit. The conversion tests (real ffmpeg, DTS-like audio, B-frames) still pass. Not verified: playback of a converted stream in a real browser on your hardware, because the test browser has no H.264 or AAC decoders; if a video still fails, the new message and log line show the exact reason.
