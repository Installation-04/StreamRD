# StreamRD and Phosphor v0.25.2 — The installer installs Docker and everything else a bare Linux machine lacks

## What changes for the owner
Until now `install.sh` stopped with "docker is required but was not found" on a machine without Docker. On Linux it now installs what is missing, so on a machine with nothing on it the one command is enough:

```bash
curl -fsSL https://raw.githubusercontent.com/Installation-04/StreamRD/main/install.sh | bash
```

- **curl, tar and the certificates**, with the machine's package manager (apt, dnf, yum, zypper, pacman or apk).
- **Docker Engine and the Compose plugin.** On Debian, Ubuntu, Raspberry Pi OS, Fedora and CentOS/RHEL and their relatives, through [Docker's own installation script](https://get.docker.com), which is run as root. Where that script does not support the system, or fails, through the distribution's own packages. If the Compose plugin is still missing, Docker's release of it is downloaded and installed only if it matches the checksum published beside it.
- **The Docker service**, started now and set to start with the machine (systemd, OpenRC or `service`).
- **FUSE**, only when you choose Zurg and `/dev/fuse` is missing; the shared mount Zurg needs is now made through sudo instead of asking you to run two commands.

**Who is asked.** In a terminal you are asked once before anything is installed (sudo may ask for your password). With `--yes`, or with no terminal, it goes ahead without asking, as long as it can get root (as root, or through a sudo that works from where the script runs); otherwise it stops and says so, having installed nothing.

**Saying no.** `--no-install-docker` (or `STREAMRD_NO_INSTALL_DOCKER=1`) installs and starts nothing and stops with what is missing. `--uninstall` never installs anything. The new `--prepare` installs and starts what the machine needs and stops before any of StreamRD's folders are made.

**What it does not do.** It does not add you to the `docker` group (membership is the same as root on that machine): when Docker answers only to root, the installer runs it through `sudo` for the run, and the commands it prints at the end start with `sudo docker`. It does not open firewall ports or set up HTTPS. On a Mac or Windows machine Docker Desktop cannot be installed without a person at the screen, so the installer says what to install and stops (on Windows, run it from a WSL 2 terminal).

Running Docker's installation script as root is a real change to a machine, which is why it is announced before it runs, asked about in a terminal, and refusable with one flag. Docker does not publish a checksum for that script; it is fetched over HTTPS from `get.docker.com` and run as it arrives. If you would rather not, install Docker yourself ([instructions](https://docs.docker.com/engine/install/)) and the installer uses it as before.

## Nothing is lost or rewritten
No change to the application and no migration. A machine that already has Docker and Compose running is untouched: the installer finds them and goes on exactly as before. Only `install.sh`, its test and the documentation change.

## Upgrading
Nothing to do: the installer is read from `main` each time it is run. An installed StreamRD updates as before (`docker compose pull && docker compose up -d`, or the **Update** button).

## Verification
- **On bare images in CI**, on every pull request (`installer-bare`): Ubuntu 24.04 and Debian 12 images with no Docker and no curl run `install.sh --yes --prepare`; afterwards curl, tar, `docker` and `docker compose` exist and the Docker daemon answers.
- **`infra/test-install-script.sh`** runs the real installer in a sandbox with no Docker, package manager, sudo or init system of its own, and recording stand-ins, and checks: a bare machine as root (Docker's script, the service started, the install going on); `--no-install-docker` and its environment variable installing nothing; a missing tar installed first; the Compose plugin installed from packages, then from the release, and a download that does not match its checksum refused; a stopped Docker started (and left alone with `--no-install-docker`); Docker that answers only to root used through sudo without touching groups; a Mac without Docker told what to install; Arch's packages; Docker's script failing and falling back to packages; no root and no sudo stopping before anything is installed; `--prepare` stopping early; `--uninstall` never installing. The refusal and the checksum checks were verified to fail when the code they guard is removed.

**Not verified:** a real machine other than those images: Fedora, CentOS, RHEL, openSUSE, Arch, Alpine and a Raspberry Pi use the same code paths but their package names, services and Docker's script on them were not run; Docker Desktop on a Mac or Windows (only the message); a machine whose package manager is locked by another process.
