# StreamRD and Phosphor v0.19.0 — Links are checked, and replaced when they die

## What changes
A debrid link can stop working long after it was imported: the provider drops the torrent, a hoster removes the file. Until now you found out when someone pressed Play. Now the server checks **in the background** and deals with it.

- **Health checks.** A background job looks at a few finished imports a minute: it asks the provider for the item and fetches the resolved link. Each item is rechecked about once a day (an hour after a doubtful result, every six hours while broken, so recovery is noticed).
- **Two strikes.** Only a definite "gone" (the provider says the item no longer exists, or the link answers 404/410) counts. Timeouts, rate limits and items still downloading prove nothing and are ignored. Two "gone" answers in a row make a link **broken**; one good answer makes it healthy again. Playing a title teaches the same thing: a failed play counts as a strike, a good play heals it.
- **Switching.** A broken version is never the card shown for its title while another version works, and it comes back by itself when it recovers. Cards and title pages say **Link needs attention** for a title whose only copy is broken.
- **Replacing.** When the *only* working copy of a title with a confirmed identity is gone, a replacement **request** is created for it (or the earlier finished request is reopened), tracked by the administrator and waiting for approval like any other request, so nothing is downloaded without your say. A request an administrator rejected or cancelled is never reopened, and a title with no confirmed identity is only flagged.
- **Seeing it.** *Admin → Overview* shows **Links needing attention**; the Imports page lists the titles and has **Check again** for each. The counts and list are administrator-only.
- `LINK_HEALTH=false` turns the background job off; `LINK_HEALTH_BATCH` (default 3, at most 20) sets how many items are checked per minute.

## Nothing is deleted
A broken import is never removed or rewritten: it only carries a health state, and its watch positions and metadata stay. The database gains four columns on the imports table and an index (`20261114000000_link_health`, additive, applied after the usual automatic backup); existing items start as "not checked yet". Going back to v0.18.x ignores the columns.

## Upgrading
`docker compose pull && docker compose up -d`. Both products. Checking uses your own provider account (one lookup and one link request per item per day), so a very large library takes a while to be checked once; the first pass is spread over the day.

## Verification
New tests (both products): a working link is recorded and rechecked after a day; two "gone" answers break a link and one good answer heals it; a 404 on the resolved link counts as gone while timeouts, rate limits and downloads do not; a broken version stops being the shown card while another works and comes back when healed; a replacement request is created once, reopens an earlier finished request, and is never reopened after a rejection; no request without a confirmed identity; a run checks a few oldest-first items and ignores members' items and items still downloading; playback failures and successes feed the same state; the summary and check-now API are administrator-only and expose no provider references. The migration upgrade tests (every earlier checkpoint) and the additive-migration guard pass. Not verified: against a real provider account over days (the checks are tested against stand-ins), and a very large library's first pass.
